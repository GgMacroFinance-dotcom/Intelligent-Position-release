# 员工照不照岗位记忆摘要做（2026-11-24）

> backlog D-1 收尾：[`context-memory-design.md`](../../context-memory-design.md) 第 7 节说的“评测集的两个问题各跑两遍，中间插一次人的纠正，看第二遍是否照做，同时评测集的原有检查项不能退步”。2026-11-15 的[实测](../../memory-2026-11-15-real-run.md)没做这一项。
> 真实模型：OpenAI `gpt-6-luna`（宏观研究员，提炼、合并也用它），Responses 接口。整套跑了 3 遍，合计 0.019 美元。
> 真实数据：仓库里的 `macro-mcp`（0.2.2，本机 stdio 启动），FRED 经 WhichAPI 托管服务取。
> 环境：本机 macOS（arm64），本机起的 PostgreSQL 17，每遍用一个空的 schema。配置是 `rust/ip.example.yaml` 改了三处：沙箱 `none`、打开 `macro` 的 `env_from`、`database` 指向空 schema（另外 `demo` 数据源的路径写成了绝对路径，因为配置文件不在 `rust/` 下）。

## 怎么测

评测集 [`rust/evals/memory-follow.yaml`](../../../../rust/evals/memory-follow.yaml)，6 步按顺序跑，共用一个数据库：

1. 冒烟评测的两个问题（美国 10 年期国债最近一周、美国 CPI 加一个取不到的 2030 年 1 月），检查项和 `macro-smoke.yaml` 一样，另外要求报告里**没有**“下一步关注”。
2. 单独开一个对话，人说：“定个规矩：以后写数据点评，报告最后单独加一节‘下一步关注’，列两到三个接下来要盯的数据或事件，只写是什么、为什么要盯，不写具体日期和数字。这次不用写报告，记下就行。”
3. `remember` 这一步：不等对话凉下来，马上跑提炼和合并（`ip eval` 新加的，见下面），检查岗位记忆摘要里有“下一步关注”。
4. 新对话里再问第 1 步的两个问题，原有检查项照旧，另外要求报告里有“下一步关注”这一节。

选“下一步关注”是因为员工平时不会自己写这一节（岗位说明里的结构是结论、关键数据表、解读、风险与待观察、数据来源），照没照做一眼能判出来。2026-11-15 那次用的“收益率两位小数”分不出来，数据源本来就是两位小数。纠正是在另一个对话里说的，第二遍的对话里看不到它，员工只能从系统提示词里的岗位记忆摘要知道这条规矩。

跑法（在 `rust/` 下）：`./target/release/ip eval --config <配置> --set evals/memory-follow.yaml --out run-N.json`，要 `OPENAI_API_KEY`、`WHICHAPI_API_KEY`、`IP_DATABASE_URL`。

| 通过 | 6/6 | 6/6 | 6/6 |
| 纠正之前的两份报告有“下一步关注” | 0/2 | 0/2 | 0/2 |
| 纠正时员工调了 `memory_note` | 是 | 是 | 是 |

每一步的检查、用量、合并出来的摘要全文在 `run-N.json`（`remember` 那一项的 `reply` 是摘要）。第 1 遍纠正之后的两份报告原文在本目录：[10 年期](run-1-us-10y-week-after.md)、[CPI](run-1-us-cpi-missing-after.md)。

第 1 遍合并出的岗位记忆摘要，“干活的提示”里的一条是：

> 以后写数据点评，报告末尾单独增加“下一步关注”一节，列出两到三个接下来要关注的数据或事件，并说明关注原因；不写具体日期和数字。

## 看到的

- **第二遍都照做了，而且是从系统提示词里看到的。** 6 份报告都有“下一步关注”，每份 2 到 3 条，写的是要盯什么、为什么，没有日期和数字。第二遍的 6 个对话都没调 `memory_search`、`memory_read`，说明规矩是从系统提示词里的岗位记忆摘要来的。
- **“最后”只照做了一部分。** 6 份里 2 份把这一节放在全文最后，4 份放在“数据来源”前面。岗位说明写死了数据来源是最后一节，员工把两条要求折中了。判分只看有没有这一节，不看位置。
- **原有检查项没有退步。** 纠正之后 6 份报告的数字全部能追溯、带观测日期、结构齐全，CPI 那题都写了“未取得”。缓存命中率纠正前 77% 到 95%，纠正后 63% 到 95%；每题步数不同，这几遍分不出摘要对缓存的影响。
- **摘要很短。** 只有 3 个对话，摘要 700 到 860 字，没有把数值写进去，也没有把合并规则抄进去（2026-11-15 修过的问题没再出现）。
- 第 1 遍纠正之后的 10 年期那题，员工写完报告又用 `edit_file` 改了一次，步数多一步。

## 不能说明什么

- 只有一条规矩、一个岗位、3 个对话，规矩又是专门挑的好判的格式要求。记忆多了以后，规矩被别的内容挤掉、或者和岗位说明冲突时会怎样，没测。
- `remember` 这一步是马上提炼、合并的，没走默认的“闲置 6 小时、每小时一轮”。
- 只测了 `gpt-6-luna`，每遍 2 题。
- 判分按标题找“下一步关注”。条目的内容是人看的，没有程序检查。

## `ip eval` 加了什么

- 评测集的一步可以写 `remember: true`：不发问题，把库里还没提炼的对话都提炼掉，再合并一次，查员工所在岗位的记忆摘要（只能配 `must_contain`、`must_not_contain`）。花费按岗位当天已花的钱前后相减；提炼、合并不计 token 用量，这一步的 token 记 0。
- 评测里 `memory.min_idle_hours` 当作 0，对话刚结束就能提炼；后台定时提炼不启动，只在 `remember` 这一步跑。
- 有 `remember` 的评测集只能在空库上跑：库里已经有对话时直接拒绝，免得旧对话混进记忆，也免得碰到真实部署的记忆。

正式跑之前先用回声假模型（`evals/team-context/echo_model.py`）跑通过一遍：`remember` 提炼了 3 个对话、合并出摘要，之后两题的输入从约 200 token 涨到约 4,200 token，说明摘要进了提示词；同一个 schema 再跑一遍时按预期被拒。
