# E-9：员工知道今天是哪天（2026-11-14）

> 真实模型 `gpt-6-luna` + 真实数据（本机 `macro-mcp`，FRED 经 WhichAPI）。配置和 [E-8 的记录](../2026-11-14-e8/README.md)一样。
> 这次跑了 5 次 `ip eval`：正式评测集 3 遍，E-8 的探测问题 2 遍，合计约 0.03 美元。

## 问题

系统提示词里没有日期，员工不知道今天是哪天。研究员有时跑 `date` 查，有时凭印象猜。E-8 验证时有一次它以为是 2025 年 10 月，取了那一周的数据。

## 做法

发给模型的每条人、同事、系统消息，开头标上它自己的发送时间：

```
[2026-11-14 周六 13:22 UTC] 美国 10 年期国债收益率最近一周怎么走？写一份数据点评。
[2026-11-14 周六 13:23 UTC] [同事 coord-1] ……
```

交给 Codex 的记录和上下文压缩用的记录里，也在名字后面带上时间：`张三（2026-11-14 周六 13:22 UTC）：……`。系统提示词只加一句固定说明：“对话里每条消息都标了发送时间（UTC）。‘今天’‘最近’以最新一条消息的时间为准”，本身不放日期。

为什么不把日期放进系统提示词：系统提示词在每次请求的最前面，日期一变，整个前缀就和昨天的对不上，缓存全部失效（D-2）。标在消息上的时间只由消息自己的 `at_ms` 决定，同一条消息每次渲染都一样，已经缓存的前缀不会变。上线后第一次请求会因为格式变了而重建一次缓存，之后照常命中。

时间统一用 UTC，和每日预算的日界一致。

## 结果

| | 改之前（E-8 那批，43 次评测） | 改之后（5 次评测） |
| --- | --- | --- |
| 研究员跑 `date` 查日期 | 22 次 | 0 次 |
| 报告文件名里的日期 | 87 份里 37 份是当天；其余多数用的是数据的观测日期，另有 5 份明显错了（2025-10-18、2025-03-08、2025-12-31、2026-06-12、2026-07-06） | 12 份全部是当天 |
| 正式评测集 | 最终版 6/6 | 6/6 |
| 探测问题（有歧义的三题） | 最终版 5/6 | 6/6，没有主题的那题照样问人 |
| 每题的缓存命中率 | 正式评测集最终版 92%–95% | 第一遍第一题 71%（格式变了以后第一次请求，缓存要重建），其余 83%–97% |

## 性能

`sent_at` 每次约 260 纳秒（release，临时测的）。按 200 条消息的历史算，每次请求多约 50 微秒，和模型调用的秒级耗时比可以忽略，没有加 `ip bench` 基准。
