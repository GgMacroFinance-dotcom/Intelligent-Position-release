# A-3 真实验收：Slack 线程端到端（2026-11-16）

> 真实 Slack 工作区 + 真实模型（协调员 `gpt-6-astra`，研究员 `gpt-6-luna`）+ 真实 harness（`ip serve`），按[验收手册](m2-acceptance.md)第 4 节。
> 维护者和一位同事在 Slack 里操作并报告看到的样子；Claude 在服务这一侧对照日志和数据库。
> 环境：Claude 云端开发容器，没有 bubblewrap，`sandbox.mode: none`。OpenAI 的 key 由网络代理在请求 `api.openai.com` 时带上。
> **两处和手册不一样，结论要带着这两条读：**
> 1. 容器只能经 HTTPS 代理出网，而 harness 的 Socket Mode 连接不走代理（见下面“发现的问题”第 1 条）。这次在容器里起了一个本机转发器（不在仓库里）：`api_url` 指向它，它把请求原样转给 `slack.com`，只把 `apps.connections.open` 返回的 `wss://` 地址换成本机地址再按字节桥接。Slack 的请求和响应内容没有改动。
> 2. 取数工具（`macro-mcp`）的子进程连不上各官方数据源，研究员拿不到真实数据。所以这次验的是 Slack → 路由 → 协调员 → 研究员 → Slack 这条链路，**不是报告内容**；真实取数见 [2026-11-11 的记录](acceptance-2026-11-11.md)。

## 结果

时间是 UTC。“用时”指从 Slack 事件到达服务，到 `chat.postMessage` 或 `chat.update` 返回成功。

| 手册步骤 | 结果 |
| --- | --- |
| `ip check` | ✓ `渠道 slack`：两个令牌都能用，Socket Mode 可用（经转发器） |
| 1. `@ip 点评一下本月 CPI` | ✓ 命中规则“宏观数据”，宏观研究员在线程里回复，约 20 秒。✗ 数字和来源：统计局连不上，回复写的是“未取得”，没有编数字（容器网络所限） |
| 2. 线程里接着说“再看看 PPI”（不 @） | ✓ 进了原对话，没有重新分派，还是研究员回复，约 11 秒 |
| 3. 不命中规则的需求 | ✓ 交给协调员 → `create_task` 派给研究员 → 研究员写报告、`update_task` 交回 → 协调员在同一线程里汇总，全程约 57 秒。报告在研究员工作目录的 `reports/` 下。内容基于示例数据，研究员和协调员都写明了“仅供演示” |
| 4. 含糊的需求 | ✓ 协调员发了选择卡片（`ask_human`）：问题、每项的后果说明、按钮都在，推荐项高亮（维护者确认） |
| 5. 同事点卡片按钮 | ✓ 点了两次，卡片都不变；同事只看到仅本人可见的提示“只有提需求的人能选这张卡片”（同事确认文字） |
| 6. 提需求的人点按钮 | ✓ 约 0.5 秒后原卡片按钮消失，改成“<名字>（slack:U…） 选了「…」”（维护者确认）；协调员被叫回来，接着派活并在线程里汇总 |
| 7. 名单外的频道 @ip | ✓ `allow.channels` 只填测试频道后，在另一个已拉进机器人的频道里 @ip：事件到了服务（3 个信封），没有建对话，没有任何回复 |
| 8. 重启后在第 1 步的线程里续问 | ✓ 进了原对话，还是研究员回复，约 17 秒 |
| 9. 各岗位今天的花费 | 部分：经控制台用的 `/ws` 接口（`spend_today`）读到协调员约 0.30 美元、研究员约 0.013 美元。控制台只监听容器本机地址，“岗位”页没有在浏览器里看 |
| Markdown 显示 | ✓ 加粗、标题、列表、表格在 Slack 里显示正常（维护者确认），没有退回纯文字 |

手册之外多看到的一点：同事自己也 @ip 提了一个需求，服务给他单独开了一段对话、发了一张记在他名下的卡片，他自己点了以后正常选定。

整场共 42 个信封、20 次投递（消息和卡片），都成功；没有失败或重试的投递。

## 发现的问题

1. **Socket Mode 连接不走 HTTPS 代理。** Web API 调用（`reqwest`）会读 `HTTPS_PROXY`，`tokio_tungstenite::connect_async` 不会。只能经代理出网的主机上，`ip check` 的 Slack 一项能过（它只调 Web API），`ip serve` 却连不上 Socket Mode。记为 backlog E-12。
2. **Slack 应用的事件订阅没开时，没有任何提示。** 这次的应用建好后 “Event Subscriptions” 是关的，权限也比清单少两项（`users:read`、`groups:history`）。结果是连接正常、心跳正常，但 Slack 一个事件都不推，服务这边完全安静；`ip check` 也查不出来。打开事件订阅、补上权限并重装应用后恢复。手册的排错表已加上这一条。
3. **回复里的报告链接在 Slack 里点不开。** 研究员写的是工作目录里的相对路径（如 `reports/2026-11-16-….md`），在 Slack 里只是一段文字。记为 backlog E-13。
4. 小事，没有处理：
   - 经转发器的连接在 11:46、11:48 各被重置一次，服务 1–2 秒后自己重连上；分不清是代理还是 Slack 造成的。
   - 研究员有一次调 `write_file` 漏了 `path` 参数，工具报错后它自己重试成功。
   - 不 @、也不在已有线程里的频道消息会被忽略，这是设计行为（验收时有一条这样的消息）。

## 没验的

- **回复里的真实数据**（手册第 1 步“数字注明来源和数据截至日期”）：这个容器里取不到数。
- **不经转发器的直连**：要在能直接出网的主机上再跑一次才算（backlog A-5 会覆盖）。
- **私有频道和私信**：只在公开频道里测了。`groups:history` 补上了，但没有在私有频道里发消息。
- **控制台“岗位”页**：花费是从接口读的，没看页面。
- **沙箱断网**：主机没有 bubblewrap，和前两次验收一样。
- **Slack 里的 Codex**（手册第 5 节从 Slack 发起的那一步）：这次没配 Codex 引擎。
