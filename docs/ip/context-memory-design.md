## 1. 要解决什么

现在一个数字员工只知道三样东西：组织规则、岗位说明、当前这个对话的历史。换一个对话，它就不记得上次人怎么纠正过它、哪种做法行不通、这个团队习惯怎么要报告。

要补的是两件事：

1. **上下文机制**：一次模型请求里放哪些内容、按什么顺序放、每一块多大。主页把它叫 70/20/5/5 的设计理念，代码里要有一个对应的、看得见的结构。
2. **员工记忆**：跨对话留下来的东西。从已经结束的对话里提炼，下次开工时带上。

不在本文范围内：向量检索、知识库问答、把公司文档灌进来。那是“数据源”的事，走 `ip-data` 和 MCP。

## 2. 现状（以 `main` 的代码为准）

- 系统提示词由 `ip-runtime/src/prompt.rs` 的 `system_prompt` 拼出来，顺序是组织规则、岗位说明、员工身份、同事名单。越靠前越稳定，这是为了前缀缓存。
- 每轮读入最近 `history_limit`（默认 200）条消息。超过 `context_budget_chars`（默认 6 万字）时，`agent.rs` 的 `compact` 让模型把较早的一段写成摘要，存成一条 `Body::Summary` 消息，之后的请求用摘要代替那一段。
- 摘要只在同一个对话里有效。没有任何跨对话的东西。
- 存储是 SQLite（`ip-store`），已有 `messages`、`threads`、`settings` 等表和中文可用的全文检索 `messages_fts`。
- 岗位有每日预算，账本在数据库里。

## 3. Codex 是怎么做的

读的是 `openai/codex` 仓库 2026-11-11 的 `main`（提交 `e58bf8f`），许可证 Apache-2.0。相关代码在 `codex-rs/memories/`（`read`、`write` 两个 crate 和 `README.md`）、`codex-rs/ext/memories/`（读取用的提示词和工具）、`codex-rs/state/src/runtime/memories.rs`（数据库部分）、`codex-rs/config/src/types.rs`（配置项）。

它的记忆是一条在后台跑的两阶段流水线，加一条读取路径。

**阶段一：逐个对话提炼。**

- 在新会话启动时触发，后台异步跑，不挡当前会话。子代理的会话、临时会话不触发。
- 只挑“已经凉下来”的对话：默认闲置满 6 小时、不超过 10 天、每次启动最多处理 2 个。
- 每个对话先在数据库里认领（带租约），防止重复处理。失败的带退避重试。
- 把对话内容过滤后发给模型，要求返回结构化结果：一份摘要和一个文件名用的短名。没什么值得记的就返回空。
- 发给模型之前和拿到结果之后都做一遍密钥脱敏（按正则抹掉 Bearer 令牌、API key、`xxx=密钥` 这类赋值）。
- 结果存回数据库，一个对话一条。
- 额度保护：账号剩余额度低于 25% 时整条流水线不启动。

**阶段二：全局合并。**

- 全局只有一把锁，同一时间只有一个合并在跑。
- 从阶段一的结果里选一批：超过 30 天没被用过的不选；按“被用过的次数”排序，再按最近使用时间排。上限默认 256 条。
- 把选中的摘要写成文件：`rollout_summaries/` 下一个对话一个文件。
- 记忆目录本身是一个 git 仓库。每次合并前算出和上次成功合并之间的差异，写成一个 diff 文件。没有差异就直接结束，不调模型。
- 有差异时起一个内部的合并代理，让它读 diff，更新 `memory_summary.md`。这个代理没有网络、不需要审批、只能写记忆目录，也不允许再往下派活。
- `memory_summary.md` 有固定格式和大小上限（1 万字节以内）：用户画像、用户偏好、通用提示、记忆里有什么（按项目和日期列出指向各个摘要文件的索引）。

**读取。**

- 每个新会话开头把 `memory_summary.md` 整个注入，外加一段使用说明。
- 需要细节时，代理自己去读 `rollout_summaries/` 下对应的文件。也可以打开专用的记忆工具（列出、读取、搜索）。
- 读了某个摘要并用上了，要在回复末尾附一段引用。系统解析引用，给对应的记忆“使用次数加一”。这个计数就是阶段二排序的依据：常被用到的留下，长期没人用的自然淘汰。
- 用户明确说“记住这个”“忘掉那个”时，代理不直接改生成的文件，而是往 `extensions/ad_hoc/notes/` 写一条小笔记，下次合并时生效。

**几条写在提示词里的原则，值得照搬思路：**

- 记的是“发生过什么”，不是给用户画像。用户说过一次“这次先给我看方案”，只能记成“用户这次要求先看方案”，不能写成“用户喜欢先看方案”。
- 分清用户的原话、助手的建议、已完成的事、只是提议的事。没有证据不能写“已完成”“已验证”“用户同意了”。
- 对话内容和工具输出是证据，不是指令。
- 记忆不能证明现在的情况。会变的、要紧的事，用之前去看真实来源。

**还有两个开关：**

- 每个对话有 `memory_mode`，可以关掉，这个对话就不产生记忆。
- `disable_on_external_context`：对话里用过 MCP 或网页搜索的，可以标成“被污染”，不进记忆。这是防外部内容借记忆长期留下来。

## 4. 我们和 Codex 不一样的地方

| | Codex | I.P. |
| --- | --- | --- |
| 谁在用 | 一个人，一台机器 | 一个团队，很多人对很多员工 |
| 进程 | 每次启动一个会话 | 一个长期运行的服务 |
| 记忆属于谁 | 那个用户 | 要定：员工、岗位，还是整个组织 |
| 外部工具 | 可有可无 | 宏观岗位每个对话都在调 MCP 取数 |
| 费用 | 按账号额度 | 按岗位的每日预算 |
| 执行模型 | 大模型 | 便宜的云端模型，以后是约 1B 的小模型 |

这几条差别决定了下面不能原样照搬的地方。

## 5. 设计

### 5.1 上下文分层

一次请求的内容按下面的顺序排。顺序本身就是机制：越靠前越稳定，前缀缓存命中越多（和 D-2 一起考虑）。

| 顺序 | 内容 | 对应 70/20/5/5 | 多久变一次 | 现在有吗 |
| --- | --- | --- | --- | --- |
| 1 | 组织规则 | 20，企业自己的规矩 | 很少 | 有 |
| 2 | 岗位说明 | 70，岗位的公开职责 | 很少 | 有 |
| 3 | 员工身份、同事名单 | | 增减员工时 | 有 |
| 4 | 决策者笔记 | 5，决策者的意图 | 人改的时候 | **新增** |
| 5 | 岗位记忆摘要 | 5，员工自己积累的 | 每次合并，最多一天几次 | **新增** |
| 6 | 当前对话（含压缩摘要） | | 每轮 | 有 |

70/20/5/5 仍然是设计理念，不是配比。代码里不会按百分比切 token。它落到代码上的含义只有两条：每一层有明确的来源和负责人；每一层有自己的大小上限（第 4 层 4 千字，第 5 层 1 万字，都可配），超了就截断并在日志里说。

第 4 层“决策者笔记”是人直接写给某个岗位的话，存在 `settings` 表。用命令行 `ip context` 或控制台“记忆”页写。它和岗位说明的区别是：岗位说明在 `ip.yaml` 里，改它要动配置；笔记是日常的、随手的修正。员工记忆不能覆盖它。

### 5.2 记忆属于岗位

记忆按**岗位**存，不按员工，也先不做组织级（维护者 2026-11-13 已定）。

理由：同一岗位的员工是可以互换的，路由按“谁最闲”派活。按员工存的话，同一句纠正要对每个员工各说一遍。按岗位存，任何一个宏观研究员学到的，其他宏观研究员下次都知道。组织级的记忆等有第二个真实跑通的岗位再说。

协调员也是一个岗位，有自己的记忆。

### 5.3 阶段一：逐个对话提炼

思路照 Codex，触发方式和费用控制按我们的情况改。

- **触发**：服务是长期运行的，所以不是“启动时”，而是一个后台定时任务（默认每小时看一次），启动后也跑一次。
- **挑哪些对话**：闲置满 `min_idle_hours`（默认 6）、不超过 `max_age_days`（默认 10）、上次提炼之后有新消息、对话没有关掉记忆。每次最多 `max_threads_per_pass`（默认 2）个。
- **归属**：一个对话里可能有几个岗位的员工。按岗位各提炼一次，每个岗位只看它自己能看到的内容（和 `prompt::history` 现在的规则一致：别的员工的工具调用和结果不给看）。
- **输入**：人的话、本岗位员工的话、工具调用的名字和参数、工具结果截到每条 `tool_result_chars`（默认 500）字。已有的压缩摘要可以直接代替它覆盖的那一段，省 token。
- **输出**：一份摘要和一个短标题，存进新表。没什么可记的存一条“无输出”，避免反复重试。让模型输出纯文本（第一行“标题：……”，下面是正文；没什么可记的只输出“无”），不用 JSON：小模型写不稳 JSON，格式不对时整段当正文，不丢内容。
- **用哪个模型**：默认用这个岗位自己的模型，也可以单独配。费用记在这个岗位当天的账上。当天预算剩余不到 `min_budget_remaining_percent`（默认 25）时不跑，正事优先。
- **脱敏**：发出去之前和存进去之前各做一遍，规则自己写（Bearer 令牌、常见 key 前缀、`名字=值` 形式的密钥）。
- **失败**：记下失败次数和下次可重试的时间，退避重试（1 小时起，每次翻倍，最多 1 天）。失败时保留上一次成功的摘要。单进程里用一把进程内的锁就够，不需要 Codex 那套跨进程租约；但状态要落库，崩溃重启后不会重复提炼。

提炼用的提示词自己用中文写，原则按第 3 节那四条。再加一条我们自己的：**不要把数据的数值当事实记下来**。宏观报告里的数字必须来自当次的工具结果（这也是评测集的检查项），记忆里只记“哪个序列在哪个工具里、口径上踩过什么坑”，不记“10 年期收益率是多少”。

实现时和上面不同、或上面没说到的几点（第 2 步）：

- 对话摘要表不走事件日志。它是从对话里提炼出来的，丢了可以重新提炼。
- `max_threads_per_pass` 数的是“份”：一个对话在一个岗位下算一份，一份调一次模型。
- 每轮最多看最近 1000 个凉下来的对话。处理完的对话记在内存里，没有新消息就直接跳过；服务重启后会重新看一遍，但已经提炼过的不会重新调模型。
- 交给模型的对话记录有总长度上限（`input_max_chars`，默认 4 万字），超出时只留最后一段。
- 用外部引擎（Codex）的岗位，岗位自己的 `model` 可能没配，要开记忆就得写 `extract_model`，否则提炼会一直失败并退避。
- 人关掉了记忆的对话不提炼（第 6 步，见 5.6）。

### 5.4 阶段二：按岗位合并

- 每个岗位一把锁。
- **选哪些**：超过 `max_unused_days`（默认 30）没被用过的不选，没被用过的看生成时间；按使用次数排，再按最近时间排；上限 `max_summaries`（默认 256）。
- **没变化就不调模型**：把这次选中的集合（每条的对话 id 和更新时间）和上次成功合并时的集合比，再看决策者有没有新的更正笔记。都没变就结束。
- **有变化**：一次模型调用。输入是现有的岗位记忆摘要、新增和改动的对话摘要全文、被移除的对话 id 列表、待处理的更正笔记。输出是新的岗位记忆摘要，固定格式，1 万字以内：
  - 怎么和这个团队配合（只收明确说过是惯例的，或在不同对话里出现过多次的）
  - 干活的提示（踩过的坑、行之有效的做法）
  - 记忆里有什么（按日期列出各个对话摘要，一句话说明里面有什么、什么时候用得上）
- **和 Codex 不同的地方**：它起一个带文件工具的代理在 git 目录里改文件，我们第一版只做一次不带工具的模型调用，产物存数据库。原因是我们没有“内部代理在沙箱里改文件”这条现成的路，单次调用更容易测，也更适合以后换小模型。代价是对话摘要很多时一次放不下，那时再分批或改成代理。
- **用哪个模型**：合并比提炼难，默认用协调员的模型，可配。费用记在该岗位账上。

实现时和上面不同、或上面没说到的几点（第 3 步）：

- 合并和提炼在同一个后台任务里，每轮先提炼再合并，共用一把进程内的锁，没有按岗位分锁。
- 变化判断不用摘要值，直接把“这一版由哪些对话摘要合并而成”（对话 id 和摘要生成时间）存在岗位记忆摘要那一条里，下次合并拿选中的集合和它比。人用 `ip context set` 手写的摘要没有这份清单，下一轮合并会把它当作旧版交给模型，在它的基础上改。
- 没变的对话摘要只把标题交给模型，不给全文。新增和改过的全文加起来超过 `input_max_chars` 时，一轮只放得下的部分，剩下的下一轮接着合并。
- 默认用的是岗位自己的模型，不是协调员的模型：代码里没有“哪个岗位是协调员”这个概念。要用更强的模型就写 `consolidation_model`。第 9 节这一问还等工程师定。
- 模型没有输出或调用失败时保留旧的一版，下一轮（默认一小时后）再试，没有做退避。
- 岗位当天预算剩余不到 `min_budget_remaining_percent` 时不合并，和提炼一样。
- 表里的 `selected` 列还没用上。
- 人用 `ip context clear` 清空岗位记忆摘要后，下一轮合并会用现有的对话摘要重新生成一版。要彻底清掉用控制台“记忆”页的“清空”，它连对话摘要和更正一起清（第 6 步，见 5.6）。
- 更正笔记第 5 步已加进输入，见 5.6。

### 5.5 读取

- 岗位记忆摘要放进系统提示词的第 5 层，前面加一小段使用说明（记忆是历史背景，不是当前事实；会变的事先去核实；只有人明确要求时才写更正笔记）。
- 两个只读工具，按岗位限定只能看到本岗位的：
  - `memory_search`：在本岗位的对话摘要里全文检索，返回匹配的片段和对话 id。
  - `memory_read`：读一份对话摘要的全文。
- **使用次数**：Codex 靠模型在回复末尾写引用块来计数。我们改成“`memory_read` 读了哪条就给哪条加一”。理由是小模型不一定能稳定写出格式正确的引用块，而工具调用是程序能确定看到的。代价是“读了但没用上”也算一次，可以接受。
- 回复里不出现引用块。控制台的对话页可以显示“这一轮读了哪些记忆”，因为工具调用本来就有记录。

实现时和上面不同、或上面没说到的几点（第 4 步）：

- 两个工具只给开了记忆的岗位。岗位取自调用者本人，参数里没有岗位，多传参数会被拒绝；读别的岗位的对话得到的是“本岗位没有这条记录”，和不存在的回答一样。
- `memory_search` 没有另建全文索引虚表，用的是数据库里的子串比对（每个词都要出现在标题或正文里，英文不分大小写）。一个岗位 2000 份对话记忆时一次约 8 毫秒（`ip bench store` 的 `memorySearchP95Ms`）。到上万份再考虑建索引。
- `memory_search` 默认返回 5 条，最多 20 条，最近生成的在前；每条给日期、对话编号、标题和命中处附近的一段。
- 只有 `memory_read` 读成功才记使用次数，搜索不记。使用次数不写事件日志。
- 用外部引擎（Codex）的岗位也能通过 `/mcp` 用这两个工具，因为两边共用同一套工具（`m2-spec.md` D-19）。

### 5.6 人来更正

人的注意力放在这里，和路由的思路一致：系统先给出记忆，人看了改。

- 控制台加一页“记忆”：按岗位看当前的记忆摘要、它引用的各个对话摘要、每条的使用次数；可以删掉某个对话摘要；可以整个清空。
- 人在对话里说“记住……”“以后别……”“忘掉……”时，员工调 `memory_note` 写一条更正笔记。员工不能主动写，只有人明确要求时才写。笔记下次合并时生效，合并后归档。
- 人删掉的内容，合并时不能从旧摘要里再捡回来。这一点 Codex 的合并提示词里专门写了，我们也写。
- 每个对话可以关掉记忆（对话的一个属性）。

实现时和上面不同、或上面没说到的几点（第 5 步）：

- `memory_note {text}` 只给开了记忆的岗位，记到调用者自己的岗位下。一条不超过 500 字，存之前做密钥脱敏。
- “只有人明确要求时才写”除了写在工具说明里，程序还挡三样：这一轮必须是人的消息引起的（系统消息、任务回报、同事的消息引起的一轮不能记）；外部渠道进来的对话不能记（除非 `include_channels` 打开），从它派出去的执行对话也算（顺着任务的 `origin_thread_id` 往上查，来源链成环或超过 32 层按渠道处理）；一个岗位攒着没处理的更正最多 50 条。人的消息引起的一轮里，工具结果里夹带的“记住……”仍然可能骗过模型，这一点程序挡不住，靠工具说明和控制台“记忆”页让人能看到、能删。
- 合并时有待处理的更正就调模型，哪怕对话摘要没变。合并成功后标成已处理，不删除。
- 保留期内（`max_unused_days`，默认 30 天）的更正每次合并都交给模型，已处理的也给，最多最近 50 条。这样要求忘掉的内容不会被后来的对话摘要带回来。过了保留期的更正不再交给模型，它的效果只留在岗位记忆摘要里。
- 更正笔记表的编号用自增整数，写入不走事件日志。
- 更正到下一次合并才生效（默认一小时内）；工具的返回里告诉员工在这个对话里先自己照做。
- 更正笔记在控制台“记忆”页能看、能删；命令行还看不到。

控制台“记忆”页（第 6 步）做了什么，和上面不同、或上面没说到的几点：

- 页面按岗位看：这个岗位开没开记忆、决策者笔记、岗位记忆摘要（写明这一版基于多少份对话摘要）、各对话的摘要和被读过的次数、人要求的更正、关掉了记忆的对话。
- 决策者笔记和岗位记忆摘要都能直接改。人改摘要时，合并来源的记录留着，下次合并在人改过的这一版上接着改，没有新材料就不会动它。合并时模型仍然可能改写人写的句子，要长期有效的话应该写进决策者笔记。
- “抹掉”一个对话的摘要：内容删掉，表里的行留着并记成“没什么可记的”，所以这个对话没有新消息就不会重新提炼；下次合并时，摘要里只来自它的内容由模型拿掉。在那次合并之前，旧内容还在岗位记忆摘要里。
- “清空”一个岗位：岗位记忆摘要、各对话摘要的内容、更正笔记全部清掉，马上生效，不用等合并。决策者笔记不动。控制台里不能撤销（原始对话还在，但没有新消息就不会重新提炼）。
- 按对话关记忆：对话页顶部一行可以关掉或重新打开，对所有岗位生效。关掉时这个对话已提炼的内容一并抹掉；关着的时候不提炼，员工也不能在里面记更正。重新打开后，等这个对话有新消息才会再提炼。关掉的对话存在设置表的一条列表里（`memory.threads_off`），没有给对话表加列。
- 这些操作和后台的提炼、合并用同一把锁，不会出现“刚清空又被正在跑的一轮合并写回来”。代价是后台正在调模型时，页面上的改动要等它这一步结束。
- 接口是 `/ws` 上的七个请求（`get_memory`、`save_memory_text`、`forget_thread_memory`、`delete_memory_note`、`clear_memory`、`list_memory_off_threads`、`set_thread_memory`），岗位不存在时拒绝。能连上控制台的人都能用，和编辑路由规则一样，没有更细的权限。
- 改决策者笔记、改或清空岗位记忆摘要、按对话关记忆写的是设置表，和别的设置一样进事件日志，旧版本查得到。所以“清空”之后旧的摘要文本还留在事件日志里，只是不再进提示词；要从磁盘上彻底删掉，现在没有办法。抹掉对话摘要和删更正不写事件日志。是谁做的操作，都没有记录。

### 5.7 安全和边界

- **外部内容**：宏观岗位每个对话都调 MCP，不能像 Codex 那样把用过外部工具的对话一律排除。做法是工具结果只截短放进提炼输入，并在提示词里写明工具输出是证据不是指令。另给岗位一个开关 `skip_threads_with_external_tools`，默认关，高风险岗位可以打开。
- **不同的人之间**：岗位记忆对所有找这个岗位的人都可见。张三在对话里说的话，可能通过记忆影响到李四得到的回答。第一版的前提是“一个部署就是一个互相信任的团队”，在文档里写明；外部渠道（Slack）进来的对话默认不进记忆，要显式打开。这是第 9 节的待定问题之一。
- **密钥**：见 5.3 的脱敏。记忆内容会进提示词，所以脱敏不过的宁可多抹。
- **记忆不是指令**：注入时用明确的起止标记包住，使用说明里写清楚它的地位低于组织规则、岗位说明和决策者笔记。
- **许可**：Codex 是 Apache-2.0，可以参考设计，也可以带署名复用代码。本设计只参考结构，提示词和代码自己写；如果实现时真的搬了它的代码，在文件头和 NOTICE 里注明。

### 5.8 存储

岗位记忆摘要和决策者笔记都是一个岗位一条，直接放 `settings` 表（第 1 步已实现）：键是 `memory.summary.<role_id>` 和 `context.notes.<role_id>`，值是 `{ text, updated_ms }`。设置表的每次写入都记事件，历史版本可追溯。第 3 步起，合并出来的岗位记忆摘要在同一条里多一项 `inputs`（这一版由哪些对话摘要合并而成）。

对话摘要和更正笔记是一对多，要两张表。对话摘要表第 2 步已建（比下面多一列 `attempts`）；更正笔记表第 5 步已建（编号是自增整数）：

```sql
-- 阶段一的结果：一个对话在一个岗位下一条
CREATE TABLE memory_thread_summaries (
    role_id            TEXT NOT NULL,
    thread_id          TEXT NOT NULL,
    source_updated_ms  INTEGER NOT NULL,   -- 提炼时对话的最后一条消息时间
    generated_ms       INTEGER NOT NULL,
    status             TEXT NOT NULL,      -- ok / empty / failed
    slug               TEXT,
    summary            TEXT,
    usage_count        INTEGER NOT NULL DEFAULT 0,
    last_usage_ms      INTEGER,
    selected           INTEGER NOT NULL DEFAULT 0,  -- 上次成功合并时是否被选中
    retry_after_ms     INTEGER,
    PRIMARY KEY (role_id, thread_id)
) WITHOUT ROWID;

-- 人要求的更正
CREATE TABLE memory_notes (
    id          TEXT PRIMARY KEY,
    role_id     TEXT NOT NULL,
    created_ms  INTEGER NOT NULL,
    thread_id   TEXT,
    text        TEXT NOT NULL,
    applied_ms  INTEGER                      -- 合并用掉之后填
) WITHOUT ROWID;
```

对话摘要的全文检索用现有 FTS 的做法另建一张虚表（第 4 步）。更正笔记是人的话，写入走事件日志；对话摘要不走。

  min_idle_hours: 6           # 对话闲置满多久才提炼。第 2 步已有
  max_age_days: 10            # 太久以前的对话不提炼。第 2 步已有

  max_summaries: 256          # 合并时最多选多少份对话摘要。第 3 步已有
  consolidation_model: null   # 默认用岗位自己的模型。第 3 步已有

`memory.enabled` 只管岗位记忆摘要。决策者笔记是人写的，写了就生效，不受这个开关影响。

### 5.10 和上下文压缩的关系

两件事，互不替代。压缩管一个对话太长放不下；记忆管对话之间。唯一的交点是 5.3 说的：提炼时可以拿已有的压缩摘要当输入。

### 5.11 性能

- 注入最多多出 1.4 万字的系统提示词。它们排在稳定内容之后、对话之前，一天只变几次，前缀缓存仍然有效。
- 后台任务不占员工的收件箱，不挡正在进行的对话。
- 空闲员工的内存不变：记忆摘要按岗位共享一份，不是每个员工一份。
- 要加的基准（`ip bench`）：带记忆时拼系统提示词的耗时；挑选待提炼对话的查询耗时（5 万条消息的库）；`memory_search` 的 p95。

## 7. 怎么验证

- 用假模型的测试：对话凉下来之后被提炼且只提炼一次；有新消息后重新提炼；预算不足时不跑；选中的集合没变时不调模型；人删掉的内容合并后不再出现；别的岗位读不到本岗位的记忆；密钥被抹掉。
- 真实模型（第 7 步）：评测集的两个问题各跑两遍，中间插一次人的纠正（比如“报告里收益率统一写到小数点后两位”），看第二遍是否照做，同时评测集的原有检查项不能退步。
- 按仓库规则，用假模型测过的只能写“用假模型测过”。
