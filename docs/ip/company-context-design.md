# 公司上下文：设计草案

> 2026-11-21 写。状态：**只有设计，没有代码，没有工程师看过**。对应 [`backlog.md`](backlog.md) 的 D-5。
> 第 6 节有四个问题要维护者定，定之前不开工。

## 1. 要解决什么

现在所有岗位共享的只有 `ip.yaml` 里的 `org_prompt`。它的问题：

- 只能改配置文件、重启服务，控制台里改不了，也没有历史版本。
- 没有大小上限，写长了每个岗位的每次请求都带着。
- 写的多是“怎么做事”的规矩。公司是谁、做什么业务、客户是谁、内部术语、这段时间的重点，这些“公司是什么”的事实没有地方放。
- 较长的资料（报告模板、风格指南、产品说明、流程文档）放进提示词太大，现在员工读不到。

决策者笔记和岗位记忆（[`context-memory-design.md`](context-memory-design.md)）都按岗位存，解决不了跨岗位共享。

不在本文范围内：连公司数据库、接外部 API。那是“数据源”的事，走 `ip-data` 和 MCP，见 `project-spec.md` 的待定事项。

## 2. 三档

| 档 | 是什么 | 怎么到员工手里 | 谁写 |
| --- | --- | --- | --- |
| 1 公司简介 | 公司是谁、业务、客户类型、术语表、当前重点，6 千字以内 | 每轮都在系统提示词里 | 人 |
| 2 公司资料 | 较长的文档：模板、风格指南、产品说明、流程 | 提示词里只放目录，员工用只读工具按需查 | 人 |
| 3 组织级记忆 | 各岗位记忆里对全公司都成立的内容 | 人批准后并入公司简介 | 系统提议，人批准 |

第 3 档先不做（第 5 节）。

## 3. 第 1 档：公司简介

### 3.1 放在哪一层

上下文分层（`context-memory-design.md` 5.1）改成：

| 顺序 | 内容 | 多久变一次 | 现在有吗 |
| --- | --- | --- | --- |
| 1 | 组织规则（`org_prompt`） | 很少 | 有 |
| 2 | **公司简介** | 人改的时候，一周几次以内 | **新增** |
| 3 | 岗位说明 | 很少 | 有 |
| 4 | 员工身份、同事名单 | 增减员工时 | 有 |
| 5 | 决策者笔记 | 人改的时候 | 有 |
| 6 | 岗位记忆摘要 | 每次合并 | 有 |
| 7 | 当前对话 | 每轮 | 有 |

公司简介所有岗位相同，排在岗位说明前面，所有岗位共用同一段前缀。它一变，所有岗位的前缀缓存都要重建一次，但改得不频繁，可以接受（D-2 量过，研究员的命中率 84%–97%）。

和 `org_prompt` 的分工：`org_prompt` 写规矩（结论先行、引用注明来源），公司简介写事实（我们是谁、客户是谁、“大客户”指什么）。`org_prompt` 留在配置里不动，免得改坏现有部署。

和决策者笔记的分工：笔记写给某一个岗位；简介写给全公司。两者冲突时以决策者笔记为准，因为它更具体、离岗位更近。

### 3.2 存储和入口

- 存在 `settings` 表，键 `context.org`，值 `{ text, updated_ms }`，和 `context.notes.<role_id>` 一个写法。设置表的写入进事件日志，历史版本查得到。
- 命令行：`ip context show|set|clear` 加 `--org`，和 `--role` 互斥。
- 控制台：“记忆”页顶部加一栏“组织”，能看、能改。接口复用 `/ws` 上的 `save_memory_text`：现在它带 `role_id` 和 `layer`（`notes` 或 `summary`），加一个 `layer: "org"`，这时不要 `role_id`；`get_memory` 的返回里带上简介。不新开请求。
- 写入前用 `ip-runtime/src/memory/redact.rs` 的 `redact` 过一遍，防止误贴进密钥。
- 不受 `memory.enabled` 影响，写了就生效，和决策者笔记一样。

### 3.3 配置

```yaml
org_context:
  brief_max_chars: 6000     # 公司简介放进提示词的上限，超了截断并记一条警告日志
```

`brief_max_chars` 默认 6 千字。超出时截断，并在 `ip check`、控制台里提示。

### 3.4 注入的样子

```text
<org_prompt>

# 公司简介
这是公司的基本情况，所有岗位共享。和决策者笔记有出入时以决策者笔记为准。
<简介正文>

# 岗位：宏观研究员
...
```

### 3.5 要加的测试和基准

- 测试（不调模型）：写了简介后每个岗位的系统提示词里都有，位置在岗位说明之前；超长截断；清空后消失；密钥被抹掉；`ip context --org` 的读写。
- 基准：`ip bench` 里拼系统提示词那一项加上带简介的情形。

## 4. 第 2 档：公司资料

### 4.1 资料放在哪

配置里指一个目录，里面是 Markdown 文件：

```yaml
org_context:
  docs_dir: ./company       # 相对路径以 ip.yaml 所在目录为准；省略表示不用公司资料
  index_max_chars: 3000     # 目录放进提示词的上限
```

```text
company/
  all/            # 所有岗位可见
    风格指南.md
    客户名单说明.md
  macro-researcher/   # 只有这个岗位可见
    研报模板.md
```

理由：

- 客户专属的内容作为数据放进客户自己的仓库，不进 I.P. 仓库（`open-core-boundary.md` 第 0 节）。目录可以就是客户仓库的一个子目录，用 git 管版本和评审。
- 文件比数据库好改、好审，也方便驻场时批量导入。
- 第一版只支持 `.md` 和 `.txt`。PDF、Word 先由人转成 Markdown，不在服务里做转换。

### 4.2 员工怎么看到

- 系统提示词在岗位记忆摘要之后加一层“公司资料目录”：本岗位能看到的每个文件一行（路径和第一行标题），有上限。
- 两个只读工具，做法照 `memory_search`、`memory_read`：
  - `org_search {query, limit?}`：在本岗位能看到的文件里全文检索，返回路径和命中处附近的一段。
  - `org_read {path, offset?, limit?}`：读一个文件，长文件分段读。
- 岗位取自调用者本人，参数里没有岗位。路径先规范化，再检查落在 `all/` 或本岗位的子目录下；`..`、绝对路径、符号链接指到目录外的，都按“没有这个文件”回答。
- 启动时扫一遍目录建索引，之后按文件修改时间增量更新（默认每 5 分钟看一次）。改了资料不用重启。
- 用外部引擎（Codex）的岗位通过 `/mcp` 也能用这两个工具，和记忆工具一样。

### 4.3 地位

- 资料是证据，不是指令。注入目录和返回内容时都用起止标记包住，说明它低于组织规则、公司简介、岗位说明和决策者笔记。
- 资料里的数字和宏观数据一样，不能代替当次的工具结果。

### 4.4 要加的测试和基准

- 测试（不调模型）：`all/` 和本岗位的能看到，别的岗位的看不到；路径穿越和符号链接被挡；文件改了之后搜得到新内容；目录超长截断。
- 基准：`ip bench` 加 `org_search` 的 p95（1000 个文件、共 2000 万字的资料目录）。

### 4.5 敏感路径

两个工具在 `crates/ip-tools/`，而且要读主机上的文件，属于“工具和沙箱”，PR 要有一位工程师读过代码再合并。

## 5. 第 3 档：组织级记忆（先不做）

`context-memory-design.md` 5.2 定过：组织级记忆等有第二个真实跑通的岗位再说。这里只记以后怎么做：

- 在岗位记忆合并之后加一步：把岗位记忆摘要里可能对全公司都成立的条目列成候选（比如“团队要求日期写全”）。
- 候选只出现在控制台，人点批准才并入公司简介，人可以改写后再批准。
