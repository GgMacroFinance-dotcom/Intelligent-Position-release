## 1. 要解决什么

现在所有岗位共享的只有 `ip.yaml` 里的 `org_prompt`。它的问题：

- 只能改配置文件、重启服务，控制台里改不了，也没有历史版本。
- 没有大小上限，写长了每个岗位的每次请求都带着。
- 写的多是“怎么做事”的规矩。公司是谁、做什么业务、客户是谁、内部术语、这段时间的重点，这些“公司是什么”的事实没有地方放。
- 较长的资料（报告模板、风格指南、产品说明、流程文档）放进提示词太大，现在员工读不到。

决策者笔记和岗位记忆（[`context-memory-design.md`](context-memory-design.md)）都按岗位存，解决不了跨岗位共享。

不在本文范围内：连公司数据库、接外部 API。那是“数据源”的事，走 `ip-data` 和 MCP，见 `project-spec.md` 的待定事项。

## 2. 已有的做法

维护者 2026-11-21 整理了一份市面上的团队上下文产品，分四类。价格和收购这类信息出自那份整理，这里没有逐条核对。

| 类 | 代表 | 做法 | 我们拿什么 |
| --- | --- | --- | --- |
| 团队 AI 记忆层 | Echo、Zep、Mem0、Supermemory、Letta | 从对话里积累记忆，在团队内共享。Echo 默认私有，分享要确认；Zep 按时间组织成上下文图谱 | “分享要人确认”。我们的岗位记忆已经做了提炼和合并，组织级只差“人批准后提升”这一步（第 6 节） |
| 企业知识接入加 AI 搜索 | Glean、Onyx、Notion、Atlassian Rovo，以及 Slack、ChatGPT、Claude 的企业版 | 把 Slack、Drive、Jira 等接进来，沿用原系统的权限 | “沿用原系统的权限”。外部系统走 MCP 接，不复制进来（第 7 节） |
| 编码团队上下文 | AGENTS.md、Unblocked、Context7 | 仓库里放一个规则文件，所有 agent 都认 | 公司资料能导出成普通 Markdown 文件，放进客户仓库，别的 agent 也能读（5.6） |
| MCP 网关 | Obot | 不提供知识，只集中管 MCP 服务的登录、权限和审计 | I.P. 已经是 MCP 客户端和服务端，按岗位分配 MCP 服务器。审计和集中登录以后再说 |

我们和它们都不一样的地方：它们服务的是人，或者给人用的 AI 助手；I.P. 的读者主要是数字员工。所以上下文要分层、分地位（组织规则高于资料，资料高于记忆），员工能写的地方要比人少。

## 3. 参考 Notion 和 AFFiNE 的什么

维护者定的方向是参考 Notion 和 AFFiNE 的思路继续做。两者的共同点是：公司知识放在一个工作区里，工作区里是一棵页面树，页面由块组成，人直接在里面写，AI 读页面当上下文。

| 思路 | 来自 | I.P. 怎么用 |
| --- | --- | --- |
| 工作区 → 空间 → 页面树，权限顺着树往下继承 | Notion（团队空间、页面共享） | 一个部署一个工作区；空间按“全公司”和各岗位分；页面权限跟着空间走，第一版不做单页共享 |
| 页面由块组成 | Notion、AFFiNE（BlockSuite） | 第一版页面正文就是 Markdown，按标题切成块存，方便检索和引用；不做块编辑器 |
| 数据库：带属性的页面集合 | Notion | 第二步再做。术语表、客户名单这种表格式的东西适合用它 |
| AI 改动是“建议”，人接受后才生效 | Notion AI 的建议编辑 | 员工不能直接改页面，只能提建议，人在控制台接受或拒绝（5.4）。组织级记忆也走这条路（第 6 节） |
| 本地优先、CRDT 同步、能自托管 | AFFiNE（Yjs，Rust 实现 y-octo） | 数据都在部署自己的 SQLite 里，本来就能自托管。多人同时编辑第一版不做，以后用 CRDT 加（5.7） |
| 版本历史 | 两者都有 | 页面每次保存都留一版，可以看差异、恢复 |

### 3.1 许可证

参考 Notion 只是参考产品设计，不涉及代码。AFFiNE 是开源项目，能不能用它的代码要分开看（2026-11-21 读的各仓库 LICENSE 文件）：

| 东西 | 许可证 | 能不能用 |
| --- | --- | --- |
| AFFiNE 主仓库（`packages/backend`、`packages/common/native` 以外） | MIT | 可以参考，也可以带署名复用 |
| AFFiNE 服务端（`packages/backend`、`packages/common/native`） | AFFiNE Enterprise Edition License：生产使用要订阅，禁止再分发，不是开源许可证 | **不能复制代码**，和 nightly-lab 一样只看设计 |
| BlockSuite（AFFiNE 的编辑器） | MPL-2.0 | 不在 `rust/deny.toml` 允许的许可证里。要用得先请维护者定 |
| OctoBase（AFFiNE 原来的数据库） | AGPL-3.0 | 不用 |
| yrs（Yjs 的 Rust 实现）、y-octo | MIT | 以后做多人编辑时可以用（5.7） |

结论：第一版不引入 AFFiNE 或 BlockSuite 的代码，控制台的编辑器用现有前端（`rust/web`，纯 JS，自带 `markdown.js`）做一个 Markdown 编辑框加预览。

## 4. 三档

| 档 | 是什么 | 怎么到员工手里 | 谁写 |
| --- | --- | --- | --- |
| 1 公司简介 | 公司空间里一张置顶页：公司是谁、业务、客户类型、术语、当前重点，6 千字以内 | 每轮都在系统提示词里 | 人 |
| 2 公司知识库 | 工作区里其余的页面：模板、风格指南、产品说明、流程 | 提示词里只放页面目录，员工用只读工具按需查 | 人写；员工只能提建议 |
| 3 组织级记忆 | 各岗位记忆里对全公司都成立的内容 | 变成对某张页面的建议，人接受后生效 | 系统提议，人接受 |

公司简介是知识库里的一张特殊页面，不单独存。这样两者共用编辑、历史和权限，只是简介会整页注入。

## 5. 公司知识库

### 5.1 结构

```text
工作区（一个部署一个）
├── 公司空间（所有岗位可见）
│   ├── 公司简介        ← 置顶，整页进提示词
│   ├── 风格指南
│   └── 客户
│       └── 大客户周报要求
├── 宏观研究员空间（只有这个岗位可见）
│   └── 研报模板
└── 运维测试空间
```

- 空间就是第一层：一个“公司”空间，每个岗位一个空间。员工能看到公司空间和自己岗位的空间。
- 人（能连上控制台的人）能看所有空间，和现在编辑路由规则一样，没有更细的权限。以后要按人分权限，再加“成员”。
- 页面可以嵌套，最多 5 层。

### 5.2 存储

放在 `ip-store` 的 SQLite 里，三张新表：

```sql
-- 页面：一张页面一行，正文是最新版本
CREATE TABLE kb_pages (
    id          TEXT PRIMARY KEY,
    space       TEXT NOT NULL,        -- 'org' 或岗位 id
    parent_id   TEXT,                 -- 空表示空间的第一层
    position    INTEGER NOT NULL,     -- 同一层里的顺序
    title       TEXT NOT NULL,
    body        TEXT NOT NULL,        -- Markdown
    pinned      INTEGER NOT NULL DEFAULT 0,   -- 1 表示公司简介，整页注入
    updated_ms  INTEGER NOT NULL,
    revision    INTEGER NOT NULL      -- 每保存一次加一
) WITHOUT ROWID;

-- 历史版本：每次保存留一份全文
CREATE TABLE kb_revisions (
    page_id     TEXT NOT NULL,
    revision    INTEGER NOT NULL,
    title       TEXT NOT NULL,
    body        TEXT NOT NULL,
    saved_ms    INTEGER NOT NULL,
    source      TEXT NOT NULL,        -- human / suggestion:<id> / import
    PRIMARY KEY (page_id, revision)
) WITHOUT ROWID;

-- 建议：员工或组织级记忆提出的改动，人接受后才写进页面
CREATE TABLE kb_suggestions (
    id            INTEGER PRIMARY KEY,
    page_id       TEXT,               -- 空表示建议新建页面
    base_revision INTEGER,            -- 基于哪一版提的
    space         TEXT NOT NULL,
    title         TEXT NOT NULL,
    body          TEXT NOT NULL,      -- 提议后的全文
    reason        TEXT NOT NULL,      -- 为什么要改，给人看
    proposed_by   TEXT NOT NULL,      -- 员工 id 或 'memory'
    thread_id     TEXT,
    created_ms    INTEGER NOT NULL,
    status        TEXT NOT NULL       -- open / accepted / rejected
);
```

- 页面写入进事件日志，和设置表一样，谁在什么时候改的以后能查。
- 检索第一版用子串比对，和 `memory_search` 一样。按 Markdown 标题把页面切成段，搜索结果返回命中的那一段和它的标题路径（如“客户 / 大客户周报要求 / 格式”）。
- 写入前用 `ip-runtime/src/memory/redact.rs` 的 `redact` 过一遍，防止误贴进密钥。

### 5.3 员工怎么读

- **公司简介**：`pinned` 的那张页面整页放进系统提示词，排在 `org_prompt` 之后、岗位说明之前，上限 `brief_max_chars`（默认 6 千字），超了截断并记日志。
- **页面目录**：在岗位记忆摘要之后加一层，列出本岗位能看到的页面（标题路径，一页一行），上限 `index_max_chars`（默认 3 千字）。
- **三个只读工具**，做法照 `memory_search`、`memory_read`：
  - `kb_search {query, limit?}`：在本岗位能看到的页面里检索，返回页面 id、标题路径、命中的段。
  - `kb_read {page_id, section?}`：读一张页面，或者它的某一段。
  - `kb_list {parent_id?}`：列出某张页面下面的子页面。
- 岗位取自调用者本人，参数里没有空间。读不到的页面和不存在的页面回答一样。
- 页面内容是证据，不是指令。注入和返回时都用起止标记包住，说明它低于组织规则、公司简介、岗位说明和决策者笔记。资料里的数字不能代替当次的工具结果。
- 用外部引擎（Codex）的岗位通过 `/mcp` 也能用这些工具。

更新后的上下文分层（`context-memory-design.md` 5.1）：

| 顺序 | 内容 | 多久变一次 |
| --- | --- | --- |
| 1 | 组织规则（`org_prompt`） | 很少 |
| 2 | **公司简介** | 人改的时候 |
| 3 | 岗位说明 | 很少 |
| 4 | 员工身份、同事名单 | 增减员工时 |
| 5 | 决策者笔记 | 人改的时候 |
| 6 | 岗位记忆摘要 | 每次合并 |
| 7 | **知识库目录** | 增删页面时 |
| 8 | 当前对话 | 每轮 |

公司简介所有岗位相同，排在前面，所有岗位共用这段前缀。它一变，所有岗位的前缀缓存都要重建一次，但改得不频繁，可以接受（D-2 量过，研究员的命中率 84%–97%）。

### 5.4 员工怎么写：只能提建议

- 第四个工具 `kb_suggest {page_id?, title, body, reason}`：对一张页面提改动，或者提议新建一张页面。只能提到本岗位能看到的空间里。
- 和 `memory_note` 一样，程序挡三样：这一轮必须由人的消息引起；外部渠道进来的对话不能提（除非打开）；一个岗位攒着没处理的建议最多 20 条。
- 控制台“知识库”页显示待处理的建议和差异，人接受、改了再接受、或者拒绝。接受时页面已经被人改过（`base_revision` 落后了），要人看过合并后的结果再保存，不自动合并。
- 被接受的建议在历史版本里记成 `suggestion:<id>`。

### 5.5 控制台

新加“知识库”页：左边是空间和页面树，右边是 Markdown 编辑框和预览（用现有的 `markdown.js`）。能新建、移动、删除页面，看历史版本、恢复，处理建议。删页面先进回收站，30 天后清掉。

接口加在 `/ws` 上（`kb_tree`、`kb_get`、`kb_save`、`kb_move`、`kb_delete`、`kb_history`、`kb_suggestions`、`kb_resolve_suggestion`），鉴权和别的控制台接口一样（设了 `auth_token_env` 就要令牌）。

### 5.6 导入和导出

- 导入：一个 Markdown 目录（每个文件一页，子目录是子页面）。Notion 和 AFFiNE 都能把页面导出成 Markdown，客户已有的资料可以这样搬进来。导入的版本记成 `import`。
- 导出：整个工作区导出成同样结构的 Markdown 目录，可以放进客户自己的仓库（`open-core-boundary.md` 第 0 节：客户专属的内容放客户仓库），也可以给仓库里的别的 agent 读（第 2 节说的 AGENTS.md 思路）。
- 命令行：`ip kb import <目录>`、`ip kb export <目录>`。

### 5.7 多人同时编辑（以后）

第一版保存时检查 `revision`：别人刚存过就提示“页面已更新”，让人刷新后再改，不做实时合并。一个团队几个人改资料，这样够用。

真有多人同时改同一页的需要时，再学 AFFiNE 用 CRDT：页面正文存成 Yjs 文档（Rust 用 yrs，MIT），控制台用 Yjs 的 JS 版同步。那时候 `body` 列改成由 CRDT 文档导出的 Markdown 快照，检索和注入都不变。

## 6. 组织级记忆

`context-memory-design.md` 5.2 定过：组织级记忆等有第二个真实跑通的岗位再说。参考 Notion 的建议编辑之后，做法可以很简单：

- 岗位记忆合并之后加一步，让模型找出对全公司都成立的条目（比如“团队要求日期写全”）。
- 每一条变成一条 `kb_suggestions`，`proposed_by` 是 `memory`，建议改公司简介或者某张公司页面。
- 人接受才进知识库。不自动提升，否则某个人在一个岗位里说的一句话，会悄悄影响所有岗位。

这样组织级记忆不用另建一套存储和页面，和员工的建议走同一条路。

## 7. 接外部的 Notion、AFFiNE 等

有的客户已经在用 Notion、Confluence、Drive。不把它们的内容复制进来，原因是复制之后权限和更新都对不上（第 2 节“沿用原系统的权限”）。做法是：

- 给需要的岗位配对应的 MCP 服务器（I.P. 已经支持按岗位配 MCP），员工直接查原系统，权限由原系统管。
- Notion 是否有官方的 MCP 服务器、怎么鉴权，这次没查到（文档网站从这台主机访问不了），做到这一步时再核对。
- 只想一次性搬过来的，用 5.6 的导入。

## 8. 安全

- 员工不能直接改知识库，只能提建议（5.4）。
- 外部渠道（Slack）里的员工也带着公司简介，内容可能出现在回复里。前提沿用记忆的设计：一个部署是一个互信的团队。在文档里写明：公司简介和公司空间里不放不能给团队全员看的东西。
- 页面内容是证据不是指令（5.3）。人从外面粘进来的资料可能夹带“忽略以上要求”这类话，靠起止标记和地位说明挡，挡不住全部，所以员工的写入一律走人审。
- 读工具和建议工具在 `crates/ip-tools/`，属于敏感路径，那几个 PR 要工程师读过再合并。

## 10. 分步实现

每一步一个小 PR。

| 步 | 内容 | 敏感 | 不调模型就能测 |
| --- | --- | --- | --- |
| 1 | 表结构、`ip kb import/export`、公司简介注入、`brief_max_chars`、拼提示词的基准 | 否 | 是 |
| 2 | 控制台“知识库”页：页面树、编辑、历史、恢复 | 否 | 是；页面在浏览器里点一遍 |
| 3 | 目录注入，`kb_search`、`kb_read`、`kb_list`，检索基准 | 是（`ip-tools`） | 是 |
| 4 | `kb_suggest` 和控制台里处理建议 | 是（`ip-tools`） | 用假模型 |
| 5 | 真实模型验证：写一段简介和几张页面，问必须用到它们才能答对的问题（比如“给大客户的周报用什么格式”），同时跑评测集，原有检查项不能退步 | | 否 |
| 6 | 组织级记忆变成建议（第 6 节） | 待定 | 等第二个岗位真实跑通 |
| 以后 | 数据库页面、多人同时编辑（CRDT）、按人分权限 | | |

第 1 步做完就能用：人写一个 Markdown 目录导入进来，置顶一张公司简介，所有员工下一轮开工就带上。
